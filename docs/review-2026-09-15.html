一、已修复 — 功能性缺陷 会让程序表现错误，用户能直接感知

1P0重复启动会出现多个托盘图标，且有两套后台循环互相抢图标

src-tauri/src/lib.rs、全项目无任何单实例判断。

现象：再点一次快捷方式 / 安装后自动启动 / IDE 里再跑一次，会在托盘出现第 2、第 3 个图标； 每个实例各有一个 1 Hz 后台线程，都在按自己的配置重绘同一个托盘、各自跑自动清理规则。

→ 新增 src-tauri/src/single_instance.rs：Local\ 命名互斥 （按会话隔离，多用户互不影响）。第二次启动不再“静默退出什么都不做”，而是用 EnumWindows + 按可执行文件路径匹配找到已有进程的窗口并唤起（用窗口类匹配是不可靠的： 所有 Tauri/WebView 应用的窗口类都叫 WRY_WEBVIEW）。main() 里的 -clean* / -ensure-autostart 等一次性助手路径刻意豁免，否则提权助手会被自己挡住。

2P0手动清理提权重启时的竞态：新实例可能判定“已在运行”而退出

引入单实例后暴露出来的连带问题（原实现没有单实例所以不存在），必须在同一次改动里解决。

手动清理未提权时，旧实例 ShellExecuteW(runas) 后立刻 exit(0)； 新实例可能在旧进程彻底退出前就启动。若只判断“互斥体已存在”，新实例会直接退出 —— 结果是应用彻底消失，比原来的重复图标严重得多。

→ 不用 GetLastError()==ERROR_ALREADY_EXISTS 做判断，改成 WaitForSingleObject 的等待语义：普通启动超时 0，提权交接 （elevation.rs 传 -takeover）超时 15 s。 旧进程退出后内核释放互斥体，新实例拿到所有权继续启动。

3P0主界面勾选的清理区域不保存，托盘/热键/自动清理用的是另一套掩码

src/App.tsx 的 toggleRegion 原来只改 React state， 从不写回 config.reduct_mask。

现象：主界面取消勾选“工作集”后点清理，本次生效；但托盘菜单清理、Ctrl+F1、 按阈值自动清理仍然用配置里的旧掩码。重启后主界面的勾选也全部丢失。

→ 勾选立即写回 reduct_mask（“全部/默认/无”三个按钮同样）。 另设 maskRef 保存最新掩码，避免设置面板 300 ms 防抖保存时把旧掩码 回写覆盖掉刚选好的区域。

4P0配置值完全没有校验：0 值会让自动清理每 30 秒疯狂触发

src-tauri/src/config.rs 直接反序列化后使用，前端滑块也只限制在 UI 上。

可复现路径：autoreduct_interval_value: 0（手改 json，或旧版本留下）→ 判断式 elapsed >= 0 恒真 → 每个 30 秒冷却周期都执行一次 8 区域全量清理。 同理 autoreduct_value: 0 让阈值判断恒真； tray_level_warning >= tray_level_danger 会让托盘警告色永远不出现 （危险分支先命中）。theme/accent_color/language 还是任意字符串。

→ 新增 Config::sanitize()，在 load()、save()（落盘前） 与 save_config 命令三处统一夹紧：阈值 1–100、间隔 1–1440、警告级别强制 < 危险级别、 theme/accent/language 白名单、掩码只保留 8 个已知位、托盘动作取值、无色值高位清零、 虚拟键为 0 的热键回退为 Ctrl+F1。should_autoclean() 另加一层防御式上限。

5P0清理失败没有任何反馈，用户只看到“释放了 0 B”

src-tauri/src/memory.rs 中 8 个 NT 调用的返回码全部写成 let _ = …。

未提权、或用户取消了 UAC 时，NtSetSystemInformation 返回 STATUS_PRIVILEGE_NOT_HELD，被完全丢弃。界面/通知显示“释放了 0 B”， 用户无法区分“本来就没东西可清”和“根本没权限”，会认为工具坏了。

→ CleanResult 新增 failed: string[]，逐区域收集失败键； 界面提示追加“N 个失败”并在有失败时不再用绿色成功样式； -clean 命令行在全部区域失败时返回退出码 1（原先恒为 0，脚本无法判断）， 失败区域另打到 stderr。

6P0卷缓存刷新盲目遍历 A:–Z:，可能卡死调用线程

src-tauri/src/memory.rs 的 flush_volume_cache。

对每个盘符无差别 CreateFileW(\\?\X:\, GENERIC_WRITE)。遇到空光驱（托盘无盘）、 已断开的映射网络盘、以及永不响应的设备时，这个调用会阻塞数秒；它跑在命令线程上， 表现为界面整个卡住。原版是枚举已挂载卷，不是猜盘符。

→ 改用 GetLogicalDrives() 只遍历真实存在的盘符， 再用 GetDriveTypeW 跳过 DRIVE_CDROM / DRIVE_REMOTE / DRIVE_NO_ROOT_DIR。返回值改为 bool，打不开的卷计为失败区域（进第 5 条）。

7P0lock().unwrap() + panic = "abort"：一次 panic 会静默杀掉整个进程

全项目 20 余处 Mutex::lock().unwrap()；src-tauri/Cargo.toml 的 release 配置是 panic = "abort" + strip = true。

任何线程在持锁时 panic（后台线程、托盘回调、命令线程）都会毒化互斥体； 之后第一个取锁的地方会 panic，而 abort 让它变成一个没有窗口、没有日志的静默退出 —— 用户只会看到托盘图标凭空消失。项目本身在 CHANGELOG 里记录过这类“静默崩溃”，但没根治。

→ 新增 lock_or_recover() / lock_config()，用 unwrap_or_else(|e| e.into_inner()) 从中毒状态恢复，替换了全部取锁点。

8P0全局热键注册失败被静默吞掉，界面开关却显示“已启用”

src-tauri/src/hotkey.rs：RegisterHotKey 失败时直接 return，调用方无从得知。

组合键被其他程序占用（Ctrl+F1 很常见）时，用户打开开关、保存、看到开关是开的， 按下去毫无反应，没有任何解释。

→ run_hotkey_loop 改为 start()，注册在监听线程内完成 （WM_HOTKEY 只投递给注册它的线程队列），结果通过 channel 回传 Result<JoinHandle, HotkeyError>；lib.rs 失败时 emit("hotkey-error")，前端弹出提示并同步发系统通知。新增 HotkeyError 枚举与「虚拟键为 0」的前置校验。

9P1热键没有 MOD_NOREPEAT，长按会连续触发清理

src-tauri/src/hotkey.rs 注册时只映射了 Ctrl/Alt/Shift/Win 四个修饰位。

按住 Ctrl+F1 不放，Windows 会按系统重复频率（约 30 ms）持续投递 WM_HOTKEY， 等于每 30 ms 做一次全量内存清理 —— 这个操作会清空所有进程工作集，后果不小。 另外 should_autoclean 的 30 s 冷却只约束自动清理，管不到热键。

→ 注册时 OR 上 MOD_NOREPEAT（windows 0.58 已提供该常量）。 该位只在注册时叠加，不进配置编码，有单测固定 (mods<<16)|vk 的编码不被污染。

二、已修复 — 不合理设计与一致性问题 能用但明显别扭

10P1清理入口各写各的：托盘与热键从不更新时间戳、不落盘、不同步界面

原先 memory::clean_memory 有三组调用方： 界面命令（更新时间戳 + 落盘）、clean_from_tray（只 emit 内存信息）、 热键回调（什么都不做）、后台自动清理（自己更新时间戳 + 落盘 + emit）。

后果：间隔式自动清理可能在手动/托盘清理几秒后又触发一次（时间戳没被刷新）； 托盘清理的结果界面上看不到任何反馈；同一份配置被两条路径以不同顺序写盘。

→ 统一为 lib.rs::perform_clean(app, mask, source, is_autoclean)： 读配置 → 清理 → 更新时间戳并落盘 → emit memory-update → emit 新的 clean-done{source,result} 事件。前端监听 clean-done 为非 manual 来源补上气泡与系统通知，托盘/热键清理终于有反馈了。

11P1主界面用硬编码 70/90，与托盘里可配置的阈值不一致

src/App.tsx 的 colorForPercent 与 MetricCard 写死 90/70；托盘的 tray_level_warning / tray_level_danger 是设置项。

把危险级别改到 80 之后，托盘图标 80% 就变红，主界面仪表环还是绿的 —— 同一个数据两个结论。

→ 抽出 pressureColor(pct, warn, danger) 与 pressure 判定， 全部改用配置值（含三个迷你进度条），颜色改为引用 CSS 变量 var(--accent/warning/danger)， 不再散落硬编码色值。

12P1当前系统不支持的区域照常可选，勾了却什么也不发生

get_os_info 命令（返回 is_win8_1 / is_win10） 在后端暴露了但前端从未调用；regions.ts 只把“需 Win10+” 当静态小字显示。

在 Win8.1 上勾选“注册表缓存”“合并内存列表”，后端会静默跳过（is_win8_1_plus() && …）， 界面却把它们算进“已选 8/8”，用户不知道有 2 个从未执行。

→ regions.ts 为每个区域补 min: "any"|"win81"|"win10"， 新增 isRegionSupported() / supportedMask()； 主界面禁用不支持的区域、把提示改成“当前系统不支持”、计数分母改为“受支持的区域数”， 并且 supportedMask() 会把这些位从提交给后端的掩码中剔除。

13P1清理区域开关无法用键盘操作，读屏软件也读不到

src/App.tsx 的 RegionCard 是 <label onClick>，内部既没有 input，也没有 tabIndex。

八个清理区域是主界面最核心的交互，却只能用鼠标点。<label> 默认不进入 Tab 序列， 没有 role，读屏软件只会读出一段文本。确认弹窗也只能点遮罩关闭，Esc 无效。

→ 改为 <button type="button" role="checkbox" aria-checked>， 补 :focus-visible 焦点环与 :disabled 态样式（CSS 里同步中和了 <button> 的默认外观）；确认弹窗加 role="dialog" aria-modal 与 Esc 关闭。

14P1托盘单击与双击冲突：把双击设成“清理内存”会先把窗口弹出来

src-tauri/src/tray.rs 的 on_tray_icon_event。

Windows 一定会先投递一次单击事件、再投递双击事件。原实现单击立刻“显示窗口”、 双击再执行配置动作，所以只要双击动作不是“显示窗口”，双击就必然伴随一次窗口弹出。

→ 若双击动作就是“显示窗口”则单击立即响应（不牺牲手感）； 否则单击推迟一个系统双击间隔执行，并在检测到双击时用 AtomicU64 令牌取消。 间隔取自 GetDoubleClickTime() 并夹在 200–1000 ms，避免异常系统设置把单击动作变成“没反应”。

15P2Windows 上 TrayIcon::set_title 是空实现，相关代码是死代码

已核对依赖源码 tray-icon-0.24.2/src/platform_impl/windows/mod.rs:287： pub fn set_title<S: AsRef<str>>(&mut self, _title: Option<S>) {}。

每秒 tick 里调用的 tray.set_title(Some("87%")) 在 Windows 上什么也不做， TrayIconBuilder::title("0%") 同样。真正的百分比是通过渲染位图与 tooltip 传达的 （这两者确实生效），但代码会让人误以为图标旁有文字标签。

→ 删除 set_title 调用与 title("0%")，并加注释说明原因， 避免以后有人再“补”回来。

16P1关闭窗口无任何提示，用户以为程序退出了

src-tauri/src/lib.rs 的 on_window_event： CloseRequested → prevent_close() + hide()，仅此而已。

点右上角 × 后窗口消失、托盘还在，但没有任何一句话告诉用户“程序仍在运行、退出请用托盘菜单”。 这是托盘类应用最常见的困惑点。

→ 新增配置项 tray_tip_shown，首次关闭时 emit("hidden-to-tray")，前端弹出气泡 + 系统通知（文案在 i18n 里，四语言齐全）。 只提示一次，不打扰。

17P2托盘菜单“官方网站/Website”实际打开的是 GitHub 仓库

src/i18n/*.json 的 tray.website 与 src-tauri/src/tray.rs 里的 PROJECT_URL。

菜单项写着“官方网站 / Website / 公式サイト”，点击落到 github.com/JackPolaris/memreduct-rs（项目主页，不是官网）。 设置页的“关于”里同一个链接却写着“项目主页”，同一事实两种说法。

→ 四语言统一改为“项目主页 / 專案主頁 / Project page / プロジェクトページ”， 并把 URL 提为具名常量 PROJECT_URL。

18P2清理区域顺序前后端不一致

src-tauri/src/memory.rs::mask::names() 的顺序是 工作集→系统文件缓存→修改文件缓存→修改页列表→待机列表→低优先级待机→注册表→合并列表； src/regions.ts 是另一套顺序。

CleanResult.regions 是与界面同源的区域清单，顺序不一致会让“按结果回显区域列表” 这类后续功能出现错位。目前只用了 .length，属于潜伏问题。

→ 后端顺序对齐前端，并加单测 mask_names_order_matches_frontend_regions 固定该约定。

19P1更新清单地址写死 x86_64

src-tauri/src/updater.rs 硬编码 update-x86_64-pc-windows-msvc.json；而 tauri.conf.json 的 bundle.targets = "all"。

在 Windows on ARM（aarch64）或 32 位包上运行，检查更新会 404 —— 表现为“检查更新失败”， 用户看不出是架构不匹配。

→ 新增 target_triple()，按 std::env::consts::ARCH 映射 x86_64 / aarch64 / i686，地址由 manifest_url() 生成。

20P2英文包 status.warn 译成 “Elevated”（权限语义）

src/i18n/en-US.json："warn": "Elevated"； zh-CN 是“内存偏高”，ja-JP 是“高い”，只有英文串到了权限相关词汇。

内存占用 70–90% 时，英文用户看到的状态徽章是 “Elevated”，而同一屏的权限徽章也是 “Administrator”，语义直接冲突。

→ 改为 "High"。

21P2挂载时的闭包捕获旧 t，更新提示会用启动时的语言

useEffect(…, []) 里捕获了首帧的 startUpdateInstall， 它内部用了 t；而该 effect 只在挂载时执行一次。

启动后把语言从中文切到 English，再点更新胶囊的“下载安装”，进度提示仍是中文。

→ 命令式回调改用始终最新的 i18n.t；另用 tRef / balloonCleanResultsRef 让挂载期注册的事件监听器读到最新的语言与通知开关。

22P2系统版本每次清理都重复查询

clean_memory 会调 is_win8_1_plus() 与 is_win10_plus()，二者内部各自 RtlGetVersion 一次。

版本号在一个进程生命周期内不可能变化，属于纯浪费（虽然单次开销很小）。

→ 用 OnceLock 缓存 os_version() 结果。

23P2页文件解析中的冗余分支

src-tauri/src/memory.rs::read_pagefile_info： if entry.NextEntryOffset == 0 && !first { break; } 紧跟 if entry.NextEntryOffset == 0 { break; }。

第一个 first 变量对结果没有任何影响，纯噪音（且循环结构不一致，容易改错）。

→ 改为统一的 loop + 边界检查，语义与原实现等价。

三、已修复 — 死代码与重复实现 这次一并清掉

24P2四个前后端“看起来存在但其实不存在/永远为假”的字段

  • CleanResult.elevation_requested（Rust）：唯一赋值处恒为 false， 因为提权路径走的是“整个进程重启并 exit(0)”，根本不会返回结果。 连带前端分支与 main.elevationRequested 四语言文案一起删除。
  • Config.tray_use_antialiasing（src/api.ts）： 后端 Config 结构体里没有这个字段，CHANGELOG 也写明已移除， 但 TS 类型一直保留着它。删除。
  • config::color_to_hex：只有它自己的单测在调用，前端另有 configHex()。删除。
  • regions.ts 的 maskNames()、MASK_FREEZES：无任何引用。删除。

→ 全部清理。api.ts 的 Config 现在与后端逐字段一致， 并补上新增的 tray_tip_shown。

25P2ShellExecuteW("open") 被复制了两份

src-tauri/src/lib.rs 的 open_external 与 src-tauri/src/tray.rs 的 open_url 是同一段不安全的 Win32 调用（含同样的 static OPEN: [u16; 5] 硬编码 ASCII）。

→ 抽出 pub fn shell_open(target: &str) -> bool，两处共用。

四、已修复 — 工具链与文档 这里的问题比代码更严重

26P1图标校验脚本从不失败——它是一个“假校验”

scripts/verify_icon_png.mjs：只 console.log 像素值， 最后打印一句 “expected purple center …, must NOT be 0,0,0,0 blank”，没有任何断言、从不 exit 1。

实测运行输出：center=51,102,255,255 —— 是蓝色的，而脚本注释写的是“校验品牌紫色”。 它既没拦住历史上的空白图标，也在“校验”一个错误的颜色。

→ 改为真校验：统计不透明像素占比（阈值 5%，实测品牌图形覆盖 31–38%， 失败模式即“完全空白 = 0%”）并额外要求中心像素不透明，任一不满足即退出码 1； 同时把该步骤加进 CI 前端任务。 （第一版把阈值设成 50%，跑起来直接判现有图标不合格 —— 说明“凭直觉定阈值”也会误报， 已按实测覆盖率修正。）

27P1extract_ico_frame.py 在 Windows 上必然崩溃

scripts/extract_ico_frame.py 末行 open("/tmp/ico_frame.png", "wb")。

本项目只构建 Windows 版本，而 Windows 上没有 /tmp。实测： FileNotFoundError: [Errno 2] No such file or directory: '/tmp/ico_frame.png'。

→ 改用 tempfile.gettempdir()，并支持 argv[1] 指定路径； 顺手把路径基准改为基于脚本位置（原实现依赖当前工作目录），并把“最后一帧”修正为“最大帧” （原注释说要 128/256 帧，代码取 entries[-1]，两者不一定一致）。

28P1三套图标生成链路产物同名、颜色互不相同；README 的描述与事实相反

render_from_png.mjs、render_icon.mjs、make_icon_png.py 都会覆写 src-tauri/icons/ 下同样的 5 个 PNG，但分别产出蓝色 / 紫色 / 紫色图标。

实测证据：

}

P2 其余建议（未改动）

  • 废弃图标脚本的归置：已用 scripts/README.md 标注， 但没有删除或移动任何文件（避免误删你仍在使用的东西）。确认有效链路后， 可把 render_icon.mjs/make_icon_png.py/make_icon.py/ check_icon_png.mjs/make_ico.py 移到 scripts/legacy/， 并从 devDependencies 移除 @resvg/resvg-js（仅 render_icon.mjs 使用）。
  • 三处白名单靠人工同步：主题色/语言/主题名分别定义在 config.rs、accents.ts、i18n/index.ts。 建议加一个 CI 步骤比对三者，避免以后加一种语言却忘记放开后端白名单 （那样配置会被 sanitize() 静默改回 zh-CN）。
  • 未提权时托盘/热键清理仍无提示：现在会通过 failed 列表在气泡里 显示“N 个失败”，但不会主动请求提权（界面手动清理才会触发 UAC 重启）。 如果希望托盘路径也能一键提权，需要单独设计（不能像手动清理那样重启整个进程， 否则会打断托盘会话）。
  • 窗口位置/大小不记忆：tauri.conf.json 固定 center: true， 每次启动都回到屏幕中央。原版 Mem Reduct 会记住，属可选增强。
  • enable_memory_privileges() 忽略 ERROR_NOT_ALL_ASSIGNED： AdjustTokenPrivileges 即使一个权限都没授予也返回成功（真值在 GetLastError）。 当前后果已被 failed 列表兜住，属可选加固。
  • src-tauri/gen/ 被 gitignore：Tauri v2 惯例是提交 gen/schemas，这样编辑器里 tauri.conf.json / capabilities/*.json 有补全和校验。构建会自动重新生成，所以不影响编译。
  • 没有任何 UI 自动化测试：所有前端行为（托盘菜单、更新流程、设置持久化） 都要手工点。若要长期维护，建议加一个最小 Playwright/WebDriver 冒烟用例， 至少覆盖“加载 → 切设置 → 改语言 → 保存”。
